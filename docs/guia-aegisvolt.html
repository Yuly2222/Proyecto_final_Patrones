¿Para quién es AegisVolt?

Una plataforma web para que las empresas de reparto con camionetas eléctricas puedan reservar un cargador, pagarlo y arrancar la carga, aunque el cargador se dañe a mitad del proceso.

Cliente 1Operador de flota

Empresa de última milla en Latinoamérica (por ejemplo fleet-rapiexpress) que migró sus vehículos a eléctricos y necesita cargarlos sin perder tiempo ni dinero.

Cliente 2Electrolinera B2B

Administrador de estaciones de carga rápida que alquila sus bahías a las flotas y necesita ver el estado de cada conector.

Sectore-Mobility y Smart Grids

Movilidad eléctrica, redes eléctricas inteligentes y logística de última milla.

Los 4 problemas que resuelve

Problema del negocioCómo lo resuelve el proyecto
Cuellos de botella al reservar conectores de alta potenciaReserva con escritura condicional en DynamoDB: dos flotas nunca pueden reservar el mismo conector.

Lo que hace un usuario, en 4 pasos

Paso 1Ve las estaciones

El panel muestra cada conector: AVAILABLE RESERVED CHARGING. Se refresca cada 2 s.

Paso 2Reserva y activa

Elige flota, conector y kWh, y pulsa «Reservar y activar carga». Eso lanza la mutación GraphQL reserveAndCharge.

Paso 3Se ejecuta la SAGA

Reservar conector → cobrar billetera → encender cargador. Si algo falla, se deshace lo anterior.

Paso 4Revisa el historial

Panel de sagas con estado COMPLETED o COMPENSATED y el detalle de cada paso.

Cómo se evalúa

Sustentación oral individual. Cada pregunta del profesor vale todo o nada (correcta = 100 %, incorrecta = 0 %). La nota de cada capa es la proporción de respuestas correctas por el peso de la capa. También pedirá demos en vivo, como forzar un fallo en la SAGA o mostrar versiones del estado en S3.

Tu proyecto corre todo local: Floci (emulador de AWS, permitido en la sección 2.4 del PDF) dentro de Kubernetes de Docker Desktop. Costo 0 USD.

Reglas clave para la sustentación

TipoOrquestación

Un coordinador central (el gateway) llama a cada servicio en orden. Se eligió porque el flujo es corto, el orden importa y el estado queda en un solo lugar (aegisvolt-sagas-<env>).

Orden inversoCompensar al revés

Si falla el paso 3: primero refund en billing y después release en reservation. Si falla el paso 2: solo release.

ReintentosHasta 3 veces

Solo ante fallos transitorios (red, 5xx). Si una compensación agota los intentos queda COMPENSATION_FAILED y Prefect lo reporta.

Idempotencia: hacerlo 2 veces = hacerlo 1 vez

OperaciónCómo se garantiza en DynamoDB
reserveConditionExpression: status = AVAILABLE OR saga_id = :mi_saga
chargeTransacción: Put TXN#<saga>#CHARGE con attribute_not_exists(pk) + descuento. Si el TXN ya existe, se cancela todo.
refundIgual, con TXN#<saga>#REFUND: solo puede existir uno.
releasesaga_id = :mi_saga; si ya se liberó responde ALREADY_RELEASED.
startattribute_not_exists(session_id) con session_id = saga_id.

La llave es el saga_id y se aplica en la base de datos, no en memoria, así que funciona con varias réplicas. Lo prueba test_compensations_are_idempotent.

Feature flags por ambiente

Cada ambiente tiene su propia tabla aegisvolt-flags-<env>. Cambia un interruptor: solo afecta a esa columna. Así respondes la pregunta «cambie una flag en dev sin redesplegar y muestre que prod sigue intacto».

Flagdevtestprod

¿Por qué no hace falta redesplegar?

Los servicios leen la flag desde DynamoDB en cada request, con una caché de 3 segundos (services/common.py). Terraform crea los valores iniciales en infra/modules/dynamodb/seed.tf (surge en true para dev y test, false en prod) y usa ignore_changes = [item] para no revertir los cambios hechos en caliente.

aws dynamodb update-item --table-name aegisvolt-flags-dev --key file://flagkey.json --update-expression "SET enabled = :e" --expression-attribute-values file://flagval.json

Gobernanza de Git y promoción

El código solo avanza en una dirección y siempre por Pull Request. Haz clic en cada rama.

— PR → — PR → — PR →
El job promotion-guard rechaza cualquier PR que no sea feature/*|fix/* → dev, dev → test o test → prod. Por ejemplo feature/x → prod no se puede fusionar.

Pipeline

Antes del merge (.github/workflows/pr-checks.yml, en cada PR). Los 6 deben estar en verde:

promotion-guardValida el origen y destino del PR.
lint-buildCompila, construye imágenes Docker, exporta el esquema GraphQL, helm lint.
unit-testsLógica de negocio y compensaciones SAGA.
integration-testsContra tablas DynamoDB y GraphQL.
e2e-testsFlujo completo desde la API.
terraform-planWorkspace = github.base_ref (rama destino).

Después del merge (.github/workflows/deploy.yml): ENVIRONMENT: ${{ github.ref_name }} → terraform workspace select -or-create "$ENVIRONMENT" → terraform apply -auto-approve → scripts/deploy.sh (canary).

Canary deployment

El Service de Kubernetes selecciona solo por app=<svc>, así que reparte el tráfico según el número de pods: 4 stable + 1 canary ≈ 20 %. Prueba los dos resultados:

stable v1 · 100 %

Condiciones para pasar de 20 % a 100 % (todas, en canary_healthy): pods canary pasan readiness /health, 0 reinicios, 0 respuestas no-200 en 40 consultas GraphQL, y errores level=ERROR en CloudWatch del canary ≤ 0. Si algo falla: helm rollback.
